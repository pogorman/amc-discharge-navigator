Add it as a new section at the bottom of this page, numbered sequentially, with Status, Date, Context, Decision and Consequences. To reverse a decision, mark the old one Superseded rather than deleting it. A decision O'G has stated once is final; don't reopen it here without him.

0002: All data in Dataverse; no mock EHR, no Azure Functions

  • Status: Accepted
  • Date: 2026-10-15

Context

This is demoware for a recorded enablement session. A realistic architecture would read the chart from an EHR (FHIR) and might put logic in Azure Functions. Both add moving parts that don't change what the audience sees.

Decision

The easiest working path wins. Three Dataverse tables hold everything: amc_patient stands in for the EHR, amc_dischargeplan is the coordination record, and amc_dischargetask holds tasks and barriers. Synthetic data comes from scripts/seed_data.py, relative to an anchor date. The LACE score is computed in the seed script, not by a model.

Consequences

  • The agent, the canvas app and the Code App all work on the same rows, which is what ADR-0012 shows on camera.
  • No custom backend to deploy or secure.
  • Dates go stale, so the data is re-seeded on recording day (runbook).
  • Details: Dataverse.

0003: Reach Foundry through APIM with a managed identity

  • Status: Accepted
  • Date: 2026-10-15

Context

The tenant enforces disableLocalAuth=true on Cognitive Services, so Foundry has no API keys (KI-01). A Power Platform custom connector can't easily get an Entra token for Foundry on behalf of the agent.

Decision

Put APIM cuh-discharge-apim (Consumption) in front of Foundry. Its system-assigned identity has Cognitive Services User on cuh-discharge-foundry, and API /foundry has a managed-identity authentication policy. Callers use the APIM subscription discharge-navigator.

Consequences

  • Entra ID all the way from APIM to Foundry; key-based access stays off on the model service.
  • The connector authenticates to APIM with a subscription key, which lives only in the connection (runbook).
  • One more resource to provision (infra/provision-apim.sh, infra/apim_config.py), and the policy XML can't be handled with az rest on Windows (KI-13).

0004: Custom connector "Foundry Deployments" instead of native Foundry model prompts

  • Status: Accepted
  • Date: 2026-10-15

Context

Copilot Studio's built-in way to add a Foundry model to a prompt doesn't support GPT-5-family models (per Microsoft Learn, Oct 2026), and we want gpt-5.5 for the prior-auth packet (KI-02). The GitHub Copilot harness adopted later (ADR-0006) doesn't change that: its tools are only connectors, MCP servers and workflows, and its model list doesn't include our deployments.

Decision

A Power Platform custom connector, Foundry Deployments (connector/), with one Chat completion action that calls APIM's /foundry API with Ocp-Apim-Subscription-Key. The caller passes the deployment name. It's the same pattern as the Gov Permitting Wingman demo.

Consequences

  • Any Foundry deployment works, whatever the model family.
  • The connector is in the solution; its connection reference needs customconnectorid set (KI-15).
  • pac connector create gave the connector the default new_ schema prefix. Cosmetic; not visible in the demo.

0005: One model deployment per task

  • Status: Accepted
  • Date: 2026-10-15

Context

The story is model choice: pick the right model for each job, under one gateway and one set of governance. The two drafting jobs are different: plain-language patient instructions in the patient's language, and a payer-facing prior-auth justification with citations.

Decision

  • patient-summary = Mistral-Large-3 (preview in Foundry) for the patient instructions.
  • prior-auth = gpt-5.5 (GA) for the SNF prior-auth packet.

Each skill passes its deployment name to the connector and ends the reply with the response's model field. Every output is a draft for clinician review and signature.

Consequences

  • Model choice is visible in three places: the deployment name in the tool call, the Model: line, and the Foundry deployments list.
  • Never ask a model to name itself on camera; Mistral answered "GPT" in testing (KI-09).
  • Mistral-Large-3 must be called preview on camera (preview status).
  • Details: Foundry.

0006: Build the agent on the GitHub Copilot harness, with no topics

  • Status: Accepted
  • Date: 2026-10-19

Context

The earlier build guide described a standard Copilot Studio agent built in the portal, with topics, like the Gov demo's. The GitHub Copilot harness went GA on Aug 3, 2026: instructions, tools (connectors, MCP servers, workflows) and skills, with model choice. It's the current platform story.

Decision

Consequences

  • The drafting logic lives in two skills, patient-discharge-summary and prior-auth-packet. If the orchestrator ever writes drafts itself, the fallback is harness workflows, which still aren't topics.
  • Edits go through pac copilot pull/push, and Claude publishes (runbook).
  • pac copilot init created its own solution and publisher (KI-03) and added components to the preferred solution (KI-05).
  • The Evaluate tab is preview on harness agents (KI-19).

0007: Dataverse MCP server with end-user auth, trimmed; Foundry tool with maker auth

  • Status: Accepted
  • Date: 2026-10-19

Context

The harness doesn't offer Dataverse as a knowledge source. The agent needs to read plans, patients and tasks, and save drafts back to the plan. The Foundry connection holds an APIM key that Teams users shouldn't be asked for.

Decision

  • Dataverse: the GA Microsoft Dataverse MCP server (InvokeMCP) with end-user auth, trimmed to read_query, search, describe, search_data and update_record. The trim is the allowedTools list in agent/capabilities/tools/amc_dataverse-mcp.mcs.yml.
  • Foundry: the Foundry Deployments connector's Chat completion action with maker auth, on O'G's amc-foundry-key connection.

Consequences

  • Data access runs as the signed-in user, under Dataverse security.
  • A governance line for camera: it can read and update a plan, and every tool that could delete something is off.
  • Teams users never see a key prompt. If amc-foundry-key breaks, the drafts break for everyone (runbook).
  • The first MCP call in Teams can prompt a sign-in (KI-23).

0017: Chat with the agent inside the Command Center

  • Status: Accepted. Supersedes ADR-0010.
  • Date: 2026-11-01

Context

ADR-0010 left the agent out of the Code App because the auth was unclear and a harness agent's web channel from a Code App was unverified. Since then O'G's the-agents app, in the same tenant, has called a GitHub Copilot harness agent from a Code App through the Microsoft Copilot Studio connector. O'G: "let's build the agent into the app now."

Decision

The Command Center gets an Ask Discharge Navigator button that opens a chat panel with the same published agent. It calls the agent through the Microsoft Copilot Studio connector, as the signed-in user, with no extra app registration. Because the agent is on the GitHub Copilot harness, the call uses the connector's agentic-runtime operation (KI-32). Shipped as Code App v1.2.0.

Consequences

  • One agent in Teams, Microsoft 365 Copilot and the Command Center, with the same instructions, tools and skills.
  • The operation is undocumented, so Microsoft can change or remove it. If it breaks, the button fails with an error and the rest of the app still works. The supported fallback is a Copilot Studio workflow with an agent node.
  • Replies come back whole, with no streaming, and the panel can't show a sign-in or consent card.
  • O'G tested v1.2.1 in the published app ("that worked great"). Beat 5 of the demo script now asks the agent there, in place of beat 4's question in Teams (Claude's recommendation, for O'G to confirm).

0018: An AI voice narrates the demo video: Grant, on MAI-Voice-2.1

  • Status: Accepted.
  • Date: 2026-11-03

Context

The demo video was silent, with captions carrying the story. O'G wanted it narrated from start to finish. The options were O'G's own recorded voice (personal, but every edit that moves a chapter means recording it again) or an AI voice the build can regenerate. The video is still being tweaked.

Decision

An AI voice from Azure Speech, generated by build_demo_video.py from the project's own Foundry resource (cuh-discharge-foundry2) with Entra ID sign-in, so no keys and no new Azure resources. O'G heard four samples (Andrew HD, Ava HD, Emma HD and Grant on MAI-Voice-2.1) and picked Grant (en-US-Grant:MAI-Voice-2.1): "so we can talk about how we used a microsoft model to do it." The narration lives in the script next to the captions, and the build fits the video to it: pauses, cards and held frames get as long as their lines need, and sped-up stretches play slower where a line needs room.

Consequences

  • MAI-Voice-2.1 is in public preview, so the video says so: its last line names the voice and the model, and every recording's frame says "narrated by an AI voice (MAI-Voice-2.1, preview)".
  • Grant speaks a little slower than the HD voices, and the narration fills most of the video, so it's longer than the silent cut.
  • Changing a line regenerates only that line. A build needs az signed in to the demo tenant with Cognitive Services User on the Foundry resource (KI-36).
  • The captions file is now the narration, word for word. The deck plays the video muted, so O'G can still present live, and its notes carry each slide's narration.
  • O'G can still swap in their own voice later, chapter by chapter, through the same timing.

0019: A public copy is a scrubbed snapshot, not this repo made public

  • Status: Accepted.
  • Date: 2026-11-04

Context

O'G asked whether the repo could be made public. A scan of the files and the whole history found no secrets: .env was never committed, and no keys, tokens or connection strings appear. But the docs and their history name pre-release material from the kickoff, refer to internal kickoff documents and audiences, and list the tenant, subscription and environment IDs and the admin sign-ins. 27 commits carry a work email address, and the history holds five versions of the demo video (about 250 MB). Editing the files wouldn't help, since every earlier commit keeps the old text.

Decision

This repo stays private and remains the working repo. A public copy is published as a separate repo from a snapshot that scripts/make_public_snapshot.py builds from the committed HEAD into ../amc-agent-demo-public: Claude's files and the kickoff screenshots left out, tenant-specific values swapped for <placeholders>, the internal references dropped, and a check that stops before committing if anything on its blocklist is left. The copy is one commit under O'G's GitHub no-reply address, and later runs add a commit on top. The script stays in this repo only.

Consequences

  • O'G gets Microsoft's open-source approval before the copy goes public. Claude never pushes it without his go-ahead.
  • Every edit in the script must still match; when the source text moves, the script stops and names the edit to update.
  • Images and videos aren't text-checked. The request slide's still (docs/demo-video/prompt.png) and the demo video show og-svc's environment ID, and the recordings show the demo tenant.
  • The public docs are the build's working notes, so links into the demo environment don't open for readers, and the old git tag they mention isn't in the copy.
